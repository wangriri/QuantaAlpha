# QuantaAlpha 分钟频数据接入方案

> 日期：2026-11-09  

## 一、目标

使用分钟行情挖掘日内特征，但仍按日频或约 3 个交易日调仓：

```text
t 日完整分钟数据
  → 收盘后生成日频因子 F(t)
  → t+1 开盘首次交易
  → 默认每 3 个交易日重新调仓
```

## 二、现有数据和系统情况

### 2.1 MongoDB 分钟数据

MongoDB 已有股票分钟数据：

| 数据库 | 粒度 | 集合数 | 样例覆盖时间 |
| --- | --- | ---: | --- |
| `min_1` | 1 分钟 | 6,455 | 2019-01-02 ～ 2026-11-06 |
| `min_5` | 5 分钟 | 6,303 | 同上 |
| `min_15/30/60` | 15/30/60 分钟 | 各 6,303 | 同上 |

每只股票一个集合，例如 `000001.SZ_1min`。主要字段为：

```text
trade_date, trade_time, ts_code,
open, high, low, close, pre_close, vol, amount
```

> [!NOTE]
>
> 需要特别确认：1 分钟数据每天是 241 条，时间从 `09:30` 到 `15:00`。这比通常理解的 240 根多一条，需要知道 `09:30` 和 `15:00` 的准确含义。

### 2.2 QuantaAlpha 当前能力

QuantaAlpha 当前只支持日频因子：读取 `daily_pv.h5`，生成日频 `result.h5`，再进行防未来审计和 OTO 回测。现有代码会排除分钟索引结果，因此不能直接把分钟数据塞进当前链路。

## 三、已确认的方案

### 3.1 总体流程

采用“分钟输入、分钟计算、日频输出、低频交易”：

```text
Mongo 分钟数据（只读）
  → 按交易日提取和检查
  → 因子公式直接在分钟序列上计算
  → 每只股票每天归约成一个因子值
  → 与估值、市值等日频特征按“日期 × 股票”结合
  → 输出日频 result.h5
  → 防未来审计
  → t+1 开盘交易、约 3 日调仓
```

理由：

- 符合“分钟数据挖掘、低频交易”的目标；
- 因子计算本身使用分钟数据，而不是只组合预制的日频统计字段；
- 可以复用现有因子生成、审计和回测；
- 不需要立即建设分钟级撮合、滑点和成本模型；
- 后续仍可扩展更多分钟特征。

不直接建设分钟级回测，工程改动大，而且不符合当前交易频率目标。

### 3.2 因子按公式现场计算

分钟数据不能提前只加工成“尾盘收益、日内波动率”等固定日频字段，再让 QuantaAlpha 组合。那样真正进入挖掘系统的仍然只是日频数据，分钟路径被固定，新的可挖掘空间会很小。

正确方式是：**每个候选因子先生成自己的公式，再由公式决定如何读取和计算分钟序列。**

```text
生成候选因子公式
  → 分析公式需要哪些分钟字段、时间窗口和日频字段
  → 从 Mongo 按日读取所需分钟数据
  → 按该因子公式现场计算
  → 每只股票每天得到一个最终因子值
  → 保存最终结果，不保存分钟中间特征
```

例如，系统可以生成不同的分钟公式（以下仅表示概念，正式语法待设计）：

```text
因子 A = 尾盘30分钟收益 × 尾盘成交额占比 ÷ 全天分钟波动率
因子 B = 早盘量价相关性 - 尾盘量价相关性
因子 C = 日内价格路径效率 × 分钟成交量集中度
```

这三个因子都读取同一批原始分钟数据，但计算方法由各自公式决定，不依赖提前准备好的固定特征表。

### 3.3 分钟因子与日频特征结合

分钟公式先为每只股票每天算出一个值，再与同一天的估值、市值、换手率等日频字段按 `(日期, 股票)` 对齐。**日频字段不复制到每根分钟 bar。**

```text
分钟公式结果：2026-11-06，000001.SZ，尾盘资金强度 = 0.73
日频数据：    2026-11-06，000001.SZ，pe_ttm = 8.5

组合因子 = RANK(尾盘资金强度) × RANK(1 / pe_ttm)
```

组合因子可以由一个完整公式表达：公式的分钟部分在分钟序列上计算，日频部分从 `daily_pv` 读取，最后在日频索引层完成组合。最终仍输出每只股票每天一个值。

可以探索的分钟结构包括：

- 早盘、午后、尾盘收益；
- 尾盘成交量或成交额占比；
- 分钟收益的已实现波动率；
- 上涨分钟与下跌分钟的量差；
- 分钟收益与成交量的相关性；
- 收盘价相对当日 VWAP 的偏离；
- 日内价格路径效率或反转强度；
- 成交量在各时段的集中度。

当前分钟表没有逐笔成交方向、盘口和订单大小，因此暂时不能构造分钟级“大单、小单、主买、主卖”特征。

### 3.4 分钟算子方案

算子只是提供给 AI 组合公式的计算工具，不是提前算好的固定分钟特征。

分钟版计算默认只能在同一只股票、同一个交易日内运行，不能无意中把昨天尾盘和今天开盘接在一起。现有日频算子的含义保持不变，分钟版使用 `M_` 前缀区分。

#### A. 可以直接复用的日频算子

这些算子不关心输入是日频还是分钟频，或者继续用于分钟结果转成日频后的处理，不需要修改现有实现。

| 类别 | 可复用算子 | 使用位置 |
| --- | --- | --- |
| 普通数学 | `ADD、SUBTRACT、MULTIPLY、DIVIDE、ABS、SIGN、LOG、EXP、SQRT、POW、INV、FLOOR` | 可直接用于分钟公式 |
| 最大最小 | `MAX、MIN`（多个参数） | 对同一行的多个值取最大或最小 |
| 比较 | `GT、LT、GE、LE、EQ、NE` | 可直接用于分钟条件 |
| 条件逻辑 | `AND、OR、WHERE、FILTER` | 可直接用于分钟公式 |
| 数字序列 | `SEQUENCE` | 回归或加权计算时使用 |
| 股票间比较 | `RANK、ZSCORE、SCALE、MEAN、STD、MEDIAN、SKEW、KURT` | 分钟结果变成每日值后，对当天所有股票计算 |
| 每日结果跨日计算 | `DELAY、DELTA、TS_MEAN、TS_SUM、TS_STD、TS_MAX、TS_MIN、TS_CORR` 等现有日频算子 | 对最终日频因子继续做跨日处理 |

> 现有 `MEAN、STD` 是股票之间的横截面计算，不是“一只股票全天分钟数据的均值和标准差”。日内均值和波动需要使用下面的分钟算子。

#### B. 可以在日频算子基础上改造的分钟算子

这些算子的数学逻辑可以复用，但需要增加分钟版，并改成按“股票 + 交易日”计算。参数 `20` 在分钟版中表示 20 分钟，而不是 20 个交易日。

| 类别 | 现有日频算子 | 分钟版 |
| --- | --- | --- |
| 延迟与变化 | `DELAY、DELTA` | `M_DELAY、M_DELTA` |
| 分钟收益 | `TS_PCTCHANGE` | `M_TS_PCTCHANGE` |
| 滚动均值/总和 | `TS_MEAN、TS_SUM、SUMAC` | `M_TS_MEAN、M_TS_SUM` |
| 滚动波动 | `TS_STD、TS_VAR` | `M_TS_STD、M_TS_VAR` |
| 滚动极值 | `TS_MAX、TS_MIN` | `M_TS_MAX、M_TS_MIN` |
| 滚动中位数 | `TS_MEDIAN` | `M_TS_MEDIAN` |
| 偏度与峰度 | `TS_SKEW、TS_KURT` | `M_TS_SKEW、M_TS_KURT` |
| 排名与标准化 | `TS_RANK、TS_ZSCORE` | `M_TS_RANK、M_TS_ZSCORE` |
| 分位数与稳健波动 | `TS_QUANTILE、PERCENTILE、TS_MAD` | `M_TS_QUANTILE、M_TS_MAD` |
| 极值位置 | `TS_ARGMAX、TS_ARGMIN` | `M_TS_ARGMAX、M_TS_ARGMIN` |
| 量价关系 | `TS_CORR、TS_COVARIANCE` | `M_TS_CORR、M_TS_COVARIANCE` |
| 移动平均 | `SMA、EMA、WMA` | `M_SMA、M_EMA、M_WMA` |
| 条件统计 | `COUNT、SUMIF` | `M_COUNT、M_SUMIF` |
| 连乘与衰减 | `PROD、DECAYLINEAR` | `M_PROD、M_DECAYLINEAR` |
| 高低点距离 | `HIGHDAY、LOWDAY` | `M_HIGHBAR、M_LOWBAR` |
| 分钟回归 | `REGBETA、REGRESI` | `M_REGBETA、M_REGRESI` |
| MACD | `MACD` | `M_MACD` |
| RSI | `RSI` | `M_RSI` |
| 布林带 | `BB_MIDDLE、BB_UPPER、BB_LOWER` | `M_BB_MIDDLE、M_BB_UPPER、M_BB_LOWER` |

#### C. 需要新增的日内算子和能力

现有日频系统没有“选择当天某个时间段”和“把分钟数据收成每天一个值”的能力，因此需要新增。

| 类别 | 建议算子或能力 | 用途 |
| --- | --- | --- |
| 时间段选择 | `M_SLICE` | 选择 `09:30–10:00`、`14:30–15:00` 等时段 |
| 首尾取值 | `M_FIRST、M_LAST` | 取指定时段第一条和最后一条 |
| 时段求和 | `M_SESSION_SUM` | 计算某时段成交量、成交额总和 |
| 时段均值 | `M_SESSION_MEAN` | 计算某时段平均值 |
| 时段波动 | `M_SESSION_STD` | 计算某时段标准差 |
| 时段极值 | `M_SESSION_MAX、M_SESSION_MIN` | 计算某时段最高值和最低值 |
| 时段中位数 | `M_SESSION_MEDIAN` | 计算某时段中位数 |
| 有效记录数 | `M_SESSION_COUNT` | 统计时段内有效分钟数量 |
| 时段收益 | `M_SESSION_RETURN` | 使用时段首尾价格计算收益 |
| 极值出现时间 | `M_MAX_TIME、M_MIN_TIME` | 判断高点、低点出现在早盘还是尾盘 |
| 日频输出 | `M_TO_DAILY` | 把分钟计算结果收成每只股票每天一个值 |
| 日频字段结合 | 执行器按日期和股票自动对齐 | 将分钟结果与 PE、市值、换手率等字段组合 |

#### D. 分钟算子与日频算子分开管理

分钟计算和日频计算不是同时发生，而是前后两个阶段，因此算子应分开存放和注册：

| 算子层 | 存放内容 | 运行时机 |
| --- | --- | --- |
| 公共算子 | 加减乘除、绝对值、比较、条件判断等与频率无关的函数 | 分钟阶段和日频阶段都可以调用 |
| 分钟算子 | 所有 `M_` 算子、日内时间段选择、分钟滚动和分钟转日频 | 先在当天分钟序列上运行 |
| 日频算子 | 现有 `RANK、ZSCORE、DELAY、TS_MEAN` 等日频函数 | 分钟结果已经收成每日值后运行 |

一个分钟和日频结合的因子仍然可以写成一个完整公式，但执行器需要把它拆成前后两段：

```text
第一步：执行分钟部分
分钟原始数据 → M_ 算子 → M_TO_DAILY → 每只股票每天一个分钟结果

第二步：执行日频部分
分钟结果 + PE/市值/换手率等日频字段 → 日频算子 → 最终因子值
```

分钟结果只在内存中传给日频阶段，不要求额外保存中间文件。这样既能保证计算顺序清楚，也不会增加磁盘占用。

## 四、已确认的规则

### 4.1 时间与防未来

完整的 t 日分钟数据只能生成收盘后的 `F(t)`，最早在 `t+1` 开盘交易。

```text
正确：F(t) → open(t+1) → open(t+2)
错误：F(t) → open(t) → open(t+1)
```

后者使用了尚未发生的 t 日分钟数据，属于未来泄漏。

### 4.2 复权

- 已确认：只要公式比较不同交易日的价格，就必须复权；
- 同一天内的收益和比例可以直接使用原始价格，结果不受除权影响；
- 跨日复权使用每个交易日当时对应的 `Stock_Adj_<year>.adj_factor`，不使用未来最新一天作为历史计算基准；
- 成交量和成交额保留原始口径；
- 复权是统一的数据处理规则，不再由每个因子自行选择。
- 需要有能验证因子结果是否复权正确，且没有用到未来数据的验证检查过程。

### 4.3 存储与性能

- MongoDB 是唯一的分钟原始数据源，本地不复制全量分钟数据；
- 现阶段直接只读现有 MongoDB，不另外复制数据库或增加服务器；
- 不建立持久化分钟缓存，也不保存分钟中间结果；
- 每次从 Mongo 按交易日读取一小批数据；同批候选公式可以共享当次内存数据，但不能共享一套预制分钟特征；
- 每个因子根据自己的公式现场计算，计算完立即释放分钟数据和中间变量；
- 日频特征只在合并计算时读取，不复制到每一根分钟 bar；
- 永久保存的主要是因子公式、每天一个因子值、防未来审计和回测结果；
- 允许运行变慢，以换取更低的磁盘占用。
- 先按上述方式实际运行；如果明显影响其他人使用，再根据实测情况增加查询并发、批量大小、运行时段等限制。

简化后的存储关系：

```text
MongoDB：永久保存分钟原始数据
QuantaAlpha：按日读取 → 内存计算 → 释放分钟数据
本地磁盘：只保存日频 result.h5 和评估结果
```

### 4.4 交易与股票范围

- 保持现有的整体三日调仓：建仓后持有 3 个交易日，第 4 个交易日使用最新因子整体重新选股和调仓；
- 不采用三组交错组合，现阶段不改动现有调仓实现；
- 股票范围只包含沪深 A 股，不包含北交所。

## 五、暂定规则和待确认问题

### 5.1 数据完整性检查（暂定）

- MongoDB 始终只读；数据读取到 QuantaAlpha 后，仅在内存中把 `2024-09-25 09:30:00` 和 `2024-09-25T09:30:00Z` 等时间写法转换成统一的比较格式，用于识别重复记录，不回写或修改数据库；
- 完全相同的重复记录只保留一条；内容冲突的重复记录标记为异常；
- 检查开高低收、成交量、成交额等关键字段是否为空；
- 记录每只股票每天的实际时间点数量，目前正常样例应为 241 条；
- 发现数量不对、关键字段缺失或时间重复时，先停止计算该股票当天的因子并记录原因；
- 不用前后分钟的数据填补缺失，也不为停牌日伪造分钟记录；
- 具体允许缺多少，等全市场完整扫描后再决定，现阶段不设置宽松门槛。

### 5.2 待确认的 3 个问题

1. **基础粒度**  
   以 `min_1` 为唯一权威源，自行聚合其他粒度，还是直接使用 Mongo 各粒度库？  
   建议：优先 `min_1`，但先实测容量和速度。

2. **时间标签**  
   `09:30` 和 `15:00` 分别代表什么？时间戳是 bar 开始、结束还是瞬时点？是否包含开盘和收盘集合竞价？

3. **数据何时完整**  
   每个交易日几点可以确认当天分钟数据已经完整？是否会盘后回补或次日修订？

## 六、实施步骤与验收

### 阶段 1：确认数据口径

- 确认时间标签和集合竞价；复权及临时完整性检查已按上述规则确定；
- 对全市场分钟数据做一次完整的只读质量扫描，再决定最终缺失门槛；
- 确定要实现的分钟算子、公式示例和人工验算样例。

验收：每个时间点和字段都能解释，241 条记录问题有明确答案。

### 阶段 2：建立分钟读取和因子计算能力

- 只读提取 Mongo 分钟数据；
- 按交易日流式读取，不落地、不缓存分钟数据；
- 实现最终确认的分钟算子；
- 每个候选因子按自己的公式直接在分钟序列上计算，不依赖预制分钟特征；
- 支持同一公式同时引用分钟计算结果和日频字段；
- 每只股票每天输出一个因子值和覆盖率；
- 计算完一个日期批次后立即释放内存。

验收：重复运行结果一致；运行后没有遗留分钟数据文件；因子结果与人工样例一致。

### 阶段 3：接入因子生成和防未来审计

- 让因子生成器能够生成合法的分钟序列公式及分钟+日频组合公式；
- 校验公式引用的分钟字段、窗口、日频字段和最终归约方式；
- 生成日频 `result.h5`；
- 增加分钟截断检查和现有日频截断检查。

验收：未来分钟不会改变历史截点结果，因子时间严格早于交易时间。

### 阶段 4：运行日频/3 日评估

- 按 `F(t) → open(t+1)` 对齐；
- 使用现有整体三日调仓方式，不改动调仓逻辑；
- 只对沪深 A 股进行评估；
- 处理停牌、开盘涨跌停和无法成交；
- 记录换手、成本和数据版本。

验收：没有未来泄漏；增量与全量重算一致；正式评估不使用 debug 数据。

## 七、讨论记录

```text
1. 粒度：__min_1__
2. 09:30/15:00 与 bar 标签定义：
__09:30———— bar [09:25] 就是当天开盘价。15:00————bar （14:59-15:00]。____
3. 日终数据完整时间与修订规则：___每天早上10点会获取昨天的分钟K_____
```
